# AI Product Council: созвон агентов для проектирования B2B SaaS

## Идея проекта

Проект представляет собой мультиагентную систему, имитирующую рабочий созвон IT-команды по созданию нового B2B SaaS-продукта.

Живой пользователь выступает в роли основателя или заказчика: он описывает идею продукта, вводные ограничения и желаемый результат. Далее несколько ИИ-агентов с разными профессиональными ролями обсуждают идею, задают вопросы, спорят, предлагают MVP, оценивают риски и в конце формируют согласованный проект-план.

## Почему проект подходит под требования

В проекте сохраняются ключевые технические элементы:

- несколько ИИ-агентов с разными ролями;
- асимметрия информации: каждый агент получает свой профессиональный контекст;
- фаза обсуждения и убеждения;
- фаза коллективного решения;
- оркестратор, управляющий ходом встречи;
- структурированные ответы агентов;
- хранилище состояния обсуждения;
- использование локальной LLM через API;
- возможность подключения RAG-документов.

## Роли агентов

### Product Manager

Отвечает за ценность продукта, целевую аудиторию, пользовательские сценарии, формулировку MVP и приоритеты.

### B2B Sales / GTM Lead

Оценивает рынок, ICP, модель продаж, сегменты клиентов, возможную цену и каналы выхода на рынок.

### Tech Lead / Architect

Оценивает техническую реализуемость, архитектуру, стек, интеграции, API, сложность разработки и масштабирование.

### UX Researcher / Designer

Анализирует пользовательские боли, сценарии использования, onboarding, интерфейс и удобство для конечных пользователей.

### Security / Compliance Expert

Проверяет риски безопасности, работу с данными, требования enterprise-клиентов, GDPR, SOC2 и права доступа.

### Finance / Ops Analyst

Оценивает бюджет, стоимость разработки, поддержку, unit economics, операционные риски и ресурсы команды.

### Skeptic / Risk Officer

Ищет слабые места идеи, противоречия, риски провала, неочевидные ограничения и причины не запускать проект.

## Роль живого пользователя

Живой пользователь может выступать как Founder / CEO. Он:

- вводит исходную идею SaaS-продукта;
- отвечает на уточняющие вопросы агентов;
- наблюдает за обсуждением;
- принимает или корректирует итоговое решение.

## Фазы работы системы

### 1. Ввод идеи

Пользователь описывает идею B2B SaaS:

- для кого продукт;
- какую проблему решает;
- какие есть ограничения;
- какой результат ожидается.

### 2. Уточняющие вопросы

Каждый агент задаёт пользователю 1-2 вопроса со своей профессиональной позиции.

### 3. Индивидуальный анализ

Агенты по очереди оценивают идею:

- продуктовая ценность;
- рынок и продажи;
- архитектура;
- UX;
- безопасность;
- экономика;
- риски.

### 4. Обсуждение и спор

Агенты реагируют на аргументы друг друга, соглашаются, спорят, уточняют слабые места и предлагают альтернативы.

### 5. Предложения по MVP

Каждый агент предлагает, что должно войти в первую версию продукта.

### 6. Голосование и приоритизация

Агенты голосуют за одно из решений:

- запускать проект;
- запускать только после уточнений;
- не запускать;
- изменить идею или сузить MVP.

Также агенты выбирают:

- топ-3 функции MVP;
- топ-3 риска;
- главный следующий шаг.

### 7. Финальный отчёт

Оркестратор собирает итоговый документ:

- краткое описание продукта;
- целевой клиент;
- проблема и ценность;
- MVP;
- техническая архитектура;
- риски;
- план разработки на 4-6 недель;
- итоговое решение команды.

## Асимметрия информации

Чтобы проект был технически похож на «Мафию», агенты не должны получать одинаковый контекст.

Примеры скрытого или специализированного контекста:

- Sales-агент получает документ с рыночными данными и ICP;
- Tech Lead получает ограничения команды и инфраструктуры;
- Security-агент получает требования по данным, доступам и compliance;
- Finance-агент получает бюджет и ограничения по ресурсам;
- Skeptic получает список типичных причин провала SaaS-проектов;
- Product Manager получает выдержки из интервью пользователей.

Оркестратор передаёт каждому агенту только ту информацию, которая соответствует его роли. Это защищает архитектуру от смешивания контекстов и демонстрирует управление информацией.

## Оркестратор

Оркестратор — центральная программная логика. Он:

- хранит состояние встречи;
- запускает фазы обсуждения;
- формирует индивидуальный промпт для каждого агента;
- передаёт агентам только разрешённый контекст;
- собирает ответы;
- проверяет JSON-формат;
- повторяет запрос при некорректном ответе;
- агрегирует голоса;
- формирует финальный отчёт.

Лучше сделать оркестратор детерминированным кодом, а не отдельным ИИ-агентом. Это упростит отладку и сделает поведение системы предсказуемым.

## Пример структурированного ответа агента

```json
{
  "agent": "Tech Lead",
  "phase": "mvp_vote",
  "decision": "go_with_scope_limit",
  "mvp_priority": [
    "multi-tenant authentication",
    "admin dashboard",
    "CSV import"
  ],
  "main_risk": "integration complexity",
  "reason": "The product is feasible if the first version limits external integrations."
}
```

## Возможная архитектура

Компоненты системы:

- интерфейс пользователя: консоль, Streamlit, Gradio или простой веб-интерфейс;
- оркестратор встречи;
- набор агентов с системными промптами;
- локальная LLM через OpenAI-compatible API;
- RAG-документы с правилами, рынком, ограничениями и best practices;
- хранилище состояния: JSON, SQLite или in-memory словарь;
- генератор финального отчёта.

## Минимальный прототип

Минимально рабочая версия должна уметь:

1. Принять от пользователя описание SaaS-идеи.
2. Запустить 4-5 агентов.
3. Провести несколько фаз обсуждения.
4. Получить структурированные ответы в JSON.
5. Собрать голоса и приоритеты.
6. Сформировать итоговый проект-план.

## Исследовательская фишка

В качестве исследовательской части можно взять одну из задач:

- как сделать агентов не одинаковыми по стилю мышления;
- как заставить агента-скептика конструктивно критиковать, а не просто отвергать всё;
- как валидировать JSON-ответы модели;
- как разделить общий и приватный контекст агентов;
- как превратить спор агентов в полезный финальный план;
- как оценивать качество итогового SaaS-плана.

## Защита проекта

На защите можно показать:

- роли агентов и их системные промпты;
- схему архитектуры;
- пример разных контекстов для разных агентов;
- ход одного созвона;
- JSON-ответы агентов;
- итоговый проект-план;
- обоснование выбранного LLM-движка, стека и интерфейса.

## Краткая формулировка

AI Product Council — это мультиагентный симулятор продуктового совета, где ИИ-агенты с ролями Product Manager, Tech Lead, Sales, UX, Security, Finance и Skeptic обсуждают идею B2B SaaS, спорят, голосуют и формируют технически обоснованный MVP-план.

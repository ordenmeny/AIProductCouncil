# AI Product Council: созвон агентов для проектирования IT-сервиса

## Идея проекта

Проект представляет собой мультиагентную систему, которая имитирует рабочий созвон IT-команды по созданию нового сервиса, внутреннего инструмента или внедрению новой фичи в существующий продукт.

Живой пользователь выступает в роли заказчика или инициатора задачи. Он описывает идею, вводные ограничения и желаемый результат. Далее несколько ИИ-агентов с разными профессиональными ролями обсуждают задачу, задают вопросы, спорят, предлагают MVP, оценивают риски и формируют согласованный план.

## Ключевые технические элементы:
- несколько ИИ-агентов с разными ролями;
- асимметрия информации: каждый агент получает свой профессиональный контекст;
- фаза уточняющих вопросов к пользователю;
- фаза обсуждения и убеждения;
- фаза коллективного решения;
- оркестратор, управляющий ходом встречи;
- структурированные ответы агентов;
- хранилище состояния обсуждения;
- использование локальной LLM через API;
- экспорт протокола и итогового плана.

## Роли агентов

### Product/Business Manager
Расписывает MVP, выявляет целевую аудиторию, ценность продукта для пользователя, какие проблемы пользователя решает продукт и как он это решает.

### Tech Lead / Architect

Оценивает техническую реализуемость. Расписывает архитектуру, стек, интеграции, API, сложность разработки и ограничения.

### UX Researcher / Designer

Создает сценарии использования продукта.

### Security / Data Expert

Ищет риски работы с данными и предлагает минимальные меры безопасности.

### Skeptic / Risk Officer

Ищет слабые места идеи, противоречия, риски провала, неочевидные ограничения.

## Роль живого пользователя

Пользователь может выступать как заказчик, владелец процесса или инициатор фичи. Он:
- вводит исходную идею сервиса или фичи;
- задает ограничения по срокам, команде, данным или технологиям;
- отвечает на уточняющие вопросы агентов;
- наблюдает за обсуждением;
- принимает или корректирует итоговое решение.

## Фазы работы системы

### 1. Ввод идеи

Пользователь описывает задачу:

- что нужно создать или внедрить;
- для кого это нужно;
- какую проблему решает;
- какие есть ограничения;
- какой результат ожидается.

Каждый из агентов расписывет MVP (каждый со своей области).

### 2. Уточняющие вопросы

Каждый агент задаёт пользователю один важный вопрос со своей профессиональной позиции.

### 3. Индивидуальный анализ

Агенты по очереди оценивают идею с точки зрения своей профессии.

### 4. Обсуждение и спор

Агенты реагируют на аргументы друг друга, соглашаются, спорят, уточняют слабые места и предлагают альтернативы.

### 5. Предложения по MVP

Каждый агент предлагает, что должно войти в первую версию и что нужно оставить за рамками.


### 6. Голосование и приоритизация

Агенты голосуют за одно из решений:

- запускать проект;
- запускать только после уточнений;
- не запускать;
- изменить идею или сузить MVP.

Также агенты выбирают:

- ключевые функции MVP;
- ключевые риски;
- вопросы к заказчику;
- важные инсайты;
- главный следующий шаг.

### 7. Финальный отчёт

Оркестратор собирает два документа:

- протокол созвона с вопросами, ответами и репликами агентов;
- итоговый план с сутью задачи, MVP, roadmap на 4-6 недель, рисками, вопросами и инсайтами.

## Асимметрия информации

Чтобы агенты не были одинаковыми, каждый получает свой приватный контекст:
- Product Manager получает правила выделения MVP и пользовательского сценария, получает контекст проверки пользы и внедрения;
- Tech Lead получает ограничения команды и инфраструктуры;
- Security / Data Expert получает требования к данным и доступам;
- Skeptic получает список типичных причин провала IT-инициатив.

Оркестратор передаёт каждому агенту только ту информацию, которая соответствует его роли. Это демонстрирует управление контекстом и предотвращает смешивание ролей.

## Оркестратор

Оркестратор — центральная программная логика. Он:

- хранит состояние встречи;
- запускает фазы обсуждения;
- формирует индивидуальный промпт для каждого агента;
- передаёт агентам только разрешённый контекст;
- собирает ответы;
- проверяет JSON-формат;
- повторяет запрос при некорректном ответе;
- агрегирует голоса, риски, roadmap, вопросы и инсайты;
- формирует финальные Markdown-документы.

Оркестратор сделан детерминированным кодом, а не отдельным ИИ-агентом. Это упрощает отладку и делает поведение системы предсказуемым.

## Пример структурированного ответа агента

```json
{
  "agent": "Tech Lead",
  "phase": "mvp_vote",
  "decision": "go_after_clarification",
  "mvp_priority": [
    "role-based access",
    "basic request form",
    "export to document"
  ],
  "roadmap_items": [
    "Неделя 1: уточнить основной процесс",
    "Неделя 2: собрать прототип формы"
  ],
  "open_questions": [
    "Кто будет владельцем процесса согласования?"
  ],
  "insights": [
    "Главный риск не в интерфейсе, а в неясных правилах согласования."
  ],
  "main_risk": "размытый scope",
  "reason": "Проект реализуем, если первая версия покрывает один понятный сценарий."
}
```

## Возможная архитектура

Компоненты системы:

- интерфейс пользователя: Streamlit;
- оркестратор встречи;
- набор агентов с системными промптами;
- локальная LLM через OpenAI-compatible API;
- приватные контексты ролей;
- хранилище состояния: Pydantic-модели и JSON-экспорт;
- генератор протокола и финального плана.

## Минимальный прототип

Минимально рабочая версия должна уметь:

1. Принять от пользователя описание сервиса или фичи.
2. Запустить несколько агентов.**Оценивает бизнес-ценность**
3. Собрать уточняющие вопросы.
4. Принять ответы пользователя.
5. Провести несколько фаз обсуждения.
6. Получить структурированные ответы в JSON.
7. Собрать голоса, roadmap, риски, вопросы и инсайты.
8. Сформировать протокол и итоговый проект-план.

## Исследовательская фишка

В качестве исследовательской части можно взять одну из задач:

- как сделать агентов не одинаковыми по стилю мышления;
- как заставить агента-скептика конструктивно критиковать, а не просто отвергать всё;
- как валидировать JSON-ответы модели;
- как разделить общий и приватный контекст агентов;
- как превратить спор агентов в полезный финальный план;
- как оценивать качество итогового MVP-плана.

## Защита проекта

На защите можно показать:

- роли агентов и их системные промпты;
- схему архитектуры;
- пример разных контекстов для разных агентов;
- ход одного созвона;
- JSON-ответы агентов;
- протокол созвона;
- итоговый план;
- обоснование выбранного LLM-движка, стека и интерфейса.

## Краткая формулировка

AI Product Council — это мультиагентный симулятор рабочего IT-созвона, где ИИ-агенты с ролями Product Manager, Business Value, Tech Lead, UX, Security/Data и Skeptic обсуждают идею сервиса или фичи, задают вопросы заказчику, спорят и формируют MVP, roadmap, риски, вопросы и полезные инсайты.
